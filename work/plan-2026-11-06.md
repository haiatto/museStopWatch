# museStopWatch 開発計画（案）2026-11-06

## 調査で分かった前提

- **公式 Muse SDK のファームが StopWatch に対応済み**（Muse 式・フル UI）。
  - `esp32/devices/sdkconfig.muse-m5stack-stopwatch`、`components/muse/boards/board_m5stack_stopwatch.c`
  - できること: UI、プッシュトゥトーク（黄キー長押し）、設定画面、画像表示、Muse の返答音声（MP3）再生、
    実験的なリアルタイム音声通話（CONFIG_MUSE_REALTIME_VOICE）。
  - 設定画面は既にある: Wi-Fi、Sound（音量）、明るさ、Battery、Power off、Reset pairing。
  - Wi-Fi は最大8件まで保存できる（`main/wifi_known.c`）。ただし追加はスマホアプリのペアリング経由。
  - 最新 upstream: 463bd2a（2026-11-05）。参照用 clone を `upstream/muse-gadget-sdk/` に置いた。
- **SDK のビルドは ESP-IDF 6.0.3 必須**（README に「他の版は非対応」）。
  先日用意した PlatformIO（ESP-IDF 5.5.5）では SDK はビルドできない。
- kantanMuse は「かんぷれ本体（Arduino）に SDK を部品として組み込み、Link で接続」していた。
  今回は **SDK のファーム本体をフォークして、kantanMuse の機能を移植する**形になる。
- SanoTTS-jp（[ayutaz/sanoTTS-jp](https://github.com/ayutaz/sanoTTS-jp)）
  - 559K パラメータ、int8 重み 654KB（flash）、22.05kHz 出力、ESP32-S3 で RTF 約 0.47、ストリーミング合成あり。
  - **内部 RAM を多く使う**: 静的 DIRAM 約 211KB、1発話のピーク約 113KB（CoreS3 実測）。
    SDK ファームは Wi-Fi・BLE・LVGL で内部 RAM が既に厳しい（sdkconfig のコメント参照）。最大のリスク。
  - 漢字の読み（G2P）は 13.7MB の辞書が必要 → 16MB flash に OTA 2面と同居できない。
    かなだけなら 877B のテーブルで済む。
  - コードは MIT。**モデルの重みは別ライセンス**（帰属表示必須、出力の用途制限が伝播）。
    公開リポジトリに重みはコミットしない（ビルド時に取得）。配布するバイナリには帰属表示が要る。

## 段階（フェーズ）

### Phase 0: 環境
1. ESP-IDF 6.0.3 をワークスペース内（`.tools/`）に導入し、dev.ps1 を idf.py 用に作り直す。
2. SDK をフォーク（kantanMuse と同じく公式の履歴を保持した作業ブランチ）。
3. 公式の StopWatch 構成をそのままビルド・書き込みし、ペアリング・会話できることを確認する。
   書き込み前にフラッシュ全体をバックアップ。

### Phase 1: 表示（アバター＋吹き出し）
- ミニアバター＋吹き出しを移植。吹き出しには **Muse の返答テキストをそのまま**出す
  （companion.say 方式にしない）。円形 466px 画面に合わせて配置を作り直す。
- kantanMuse から: 長文のページ送り、返答の置き換え時にページを戻さない修正、作業中ステータス表示。

### Phase 2: ボイス再生コマンド
- kantanMuse の kanplay.play_audio 相当（workspace の MP3 / HLS を再生）を移植。
  SDK の minimp3 と公式 /fs/raw/ 取得を使う。Muse 側が TTS した音声を本体で鳴らせる。

### Phase 3: ローカル TTS（SanoTTS-jp）
- 最初に**実現性の確認**（SDK ファームと同居して内部 RAM が足りるか）。足りなければ方式を再検討。
- Muse から呼べる TTS コマンド（テキスト→本体で合成→再生）。

### Phase 4: Muse に渡す doc
- kantanMuse の kanplay.doc 方式（Markdown を埋め込み、1回の呼び出しで全部返す）を移植。
- 内容: 本体でできること、ツールの使い方、日本語音声認識の案（要確認）。
- 音声の前に定型文は送らない。

### Phase 5: 利便性
- Web 設定ページ（QR で開く、ブラウザ鍵の保存）、Wi-Fi の追加・切替を Web から。
- システムメニュー（SDK の設定画面を拡張する形）。マイク感度、TTS、音量など。

## 決定事項（2026-11-06 ユーザー回答）
- ビルド: ESP-IDF 6.0.3 を直接（idf.py）。PlatformIO は出荷時デモ用に残す。
- SDK: GitHub 公開フォーク haiatto/muse-gadget-sdk。ワークスペースに submodule で固定。
- SanoTTS-jp の読み: スタックちゃん等の事例（例: nnn112358/StackChan-IDF-for-SanoTTS-jp）を
  調べて、高速な構成を参考に決める。Phase 3 の最初に調査する。
- 日本語音声認識の案: ユーザーがファイルで渡す（Phase 4 の doc に入れる）。

## 日本語音声認識の案（2026-11-06 受領）
- `work/voice-asr-flow-2026-11-06.md`（ユーザーが Muse に書かせたもの）。Phase 4 の doc に入れる。
- 要点: Muse 側で届いた WAV を読み直す。第一パス ReazonSpeech K2 v2 INT8（sherpa-onnx）、
  照合は faster-whisper base（英語まじり・怪しい・行動を変える指示のときだけ）。
  両方怪しければ「暫定」と明示して言い直しを頼む。Reazon の空出力は言葉以外の音。
- 本体側の前提: ボイスノートは 16 kHz・モノラル WAV。確認済み: SDK は 16 kHz WAV（長さ不明ヘッダ = 0xFFFFFFFF）でボイスノートを送る（muse_chat_session.cpp, MUSE_AUDIO_RATE 16000）。本体側の変更は不要。

## Wi-Fi 初期設定（AP モード）メモ（2026-11-06）
- kantanMuse は元の KANTAN Play v0.7.0（公式）の機能で、本体が SoftAP（SSID kanplay-ap）になり、
  DNS で全ドメインを本体に向けるキャプティブポータルと Web サーバーで Wi-Fi を設定する（task_wifi.cpp）。
  QR から AP に参加 → ページで Wi-Fi 設定 → その後 Web でトークン入力・ペアリング開始、の流れ。
- StopWatch でも同じ方式（SoftAP＋キャプティブポータル）を Phase 5 で作る。公式ファームは
  Wi-Fi をアプリのペアリング時に渡す方式なので、両方の経路を共存させる設計にする。

## 訂正：公式ファームの Wi-Fi 設定（2026-11-06 実機でユーザー確認）
- ペアリング時だけでなく、本体の設定画面（SETTINGS > Wi-Fi）からも Wi-Fi を入れられる。
  「Scan for networks」で一覧から選ぶ、または「Other network...」で SSID 入力。画面キーボードで文字入力する。
  保存済みネットワークは一覧に印が付く（最大8件、wifi_known）。
- したがって SoftAP の Web 設定は「必須」ではなく、利便性（スマホで入力できる）のための追加になる。

## AP モード（2026-11-06 ユーザー判断）
- 公式の BLE 設定ページは PC の Chrome 向け（localhost か https が必要、iOS は Bluefy）。
- 本体の QR を読むだけでスマホから設定できる SoftAP＋Web 設定は「ある方が便利」。
  本体画面で完結しないほど設定が増えたら特に必要。Phase 5 で入れる。

## 方針変更：公式＋α（2026-11-07 ユーザー判断）

  設定画面でのトークン入力、マイクのレベルメーター等）ため、まずは「公式＋α」で進める。
- Phase 1（kantanMuse のミニアバター＋吹き出し、アバターの縮小）は当面やらない（保留）。
  返答は公式の字幕表示を使う。
