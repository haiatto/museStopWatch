# museStopWatch アイデア

## 記録ルール

- アイデアには 001 から順に番号を付けて、このファイルに追記する。
- 内容を変えるときは、同じ番号の項目を編集する。番号は振り直さない。
- 各項目には、名前・やりたいこと・具体的な動作を書く。必要に応じて呼びかけ例や未決事項も添える。
- 「状態」には、アイデアの段階と実装状況を分けて書く（例: 案 / 方向性決定 / 実装中 / 実装済み・未確認 / 確認済み / 見送り）。
- 実装したら、関係するコミットやファームの版を状態に書き足す。

  ミニアバターと吹き出しは本体が自動では出さず、アプリが使える API（表示・吹き出し・Muse の有無・返事の受け取り）を用意する。

  返す（kantanMuse の `kanplay.doc` のように、ツール説明で「最初に読む」と案内する）。
- 試作するアプリ（2026-11-08 ユーザー）：ゲーム系 3 本。
  ルール：元のゲームの素材（絵・音・キャラ・名前）は使わない。権利侵害はしない。遊び方の種類だけを参考にする。

  詳細は `work/development-status.md` の 2026-11-08。計画は `work/plans/miniapp-plan.html`。
  検討の記録は `work/miniapp-runtime-study-2026-11-07.md`、`work/miniapp-runtime-study-2026-11-08-m5gfx.md`）
- 追加の条件（2026-11-07）：アプリは複数入れたり消したりでき、ランチャーで起動できる。描画だけでなく
  本体の機能を使える。Muse は必須ではない（ミニアバター＋吹き出しの常駐はあると便利）。
- 方式（2026-11-07 ユーザー決定）：ELF（`espressif/elf_loader`、PSRAM に読み込む）。lvgl の部品は本体が出す。
- 作りたいアプリ（2026-11-08）：ゲーム、UI のある小さな電卓、鍵盤など。音・振動・加速度センサー・マイク、

  反対側、つまり右スワイプで左側に出す枠に置く。
- Muse からの管理（2026-11-08）：アプリの追加・削除・更新を Muse ができる。既存のコマンド（`display.draw_file`
  など）を流用せず、専用のツール（`app.*`）を作る。
- やりたいこと：出荷時ファームにあったデモアプリ（ストップウォッチ、流体シミュレーション、ルーレット等）のようなアプリを、
  Muse が作って、その場で StopWatch に入れて動かせるようにする。
  「OS とミニアプリ」のような形で、本体側はアプリの実行環境になる。
- 呼びかけ例：「ポモドーロタイマーのアプリを作って入れて」

#### 実現方法の候補

1. **スクリプト言語（MicroPython など）**
   - Muse がスクリプトを生成して送るだけなので、作るのが速い可能性がある。
2. **ネイティブのバイナリ（動的ライブラリ）**
   - Muse のクラウド環境（VM）でビルドできれば、バイナリも作れる可能性がある。
   - ESP32 で動的に読み込んで実行する仕組みが必要。
3. **両対応**：手軽なものはスクリプト、重いものはバイナリ。

#### 大切にしたいこと

- RAM などの制限があるので、サンドボックス的なアプリ作成環境にする
  （アプリが本体の Muse 接続や設定を壊さない、使えるメモリや API を決めておく）。
- アプリの作り方・API・制限の資料を GitHub に置き、Muse に参照させて作らせる。

#### 今後詰めること

- メモリが足りるか（特に MicroPython を同居させる場合。公式ファームは内部 RAM が既に厳しい）。
- アプリの置き場所（flash の空き：アプリ 4MB×2 の後ろに約 7.8MB ある）と、入れ方（Muse の workspace から取得など）。
- 画面・ボタン・音・センサーなど、アプリに出す API の範囲。
- 参考候補（未調査）: Espressif の ELF ローダー部品、MicroPython の組み込み、WebAssembly ランタイム（wasm3 / WAMR）。

### 004：本物の ESP32-S3 エミュレータでファームとミニアプリを動かす（Muse が遊んで試す）

- 記録日：2026-11-08
- 状態：案（大きいので保留。2026-11-08 ユーザー判断）
- やりたいこと：実機のファーム（バイナリ）を ESP32-S3 のエミュレータで動かし、Muse が作ったミニアプリを
  入れて、Muse が入力を送り画面を見て遊ぶ・試す。例：スペースで作ったアプリを入れて動かす流れ。
- 呼びかけ例：「今作ったゲームをエミュで遊んで確かめて」

#### 想定する動作

1. エミュレータ上でファームが起動し、ミニアプリを読み込んで実行する。
2. Muse（または PC のスクリプト）がタッチ・青ボタン・傾きを送り、画面（縮小画像か状態の文字）を受け取る。
3. 問題がなければ実機に入れる。

#### 調べたこと（2026-11-08、資料のみ・未試行）

- Espressif QEMU：ESP32-S3 と PSRAM（QPI / OPI）に対応。公式サポート外の fork。LCD・RGB と Wi-Fi は確認できず
  （有線 LAN の仮想デバイスで代用が一般的）。https://github.com/espressif/esp-toolchain-docs/blob/main/qemu/README.md
- Wokwi：ESP32-S3、PSRAM（8MB・octal 可）、Wi-Fi の仮想ネットワーク、カスタムチップ API あり。
  画面との組み合わせ、料金・利用条件は未確認。https://docs.wokwi.com/guides/esp32
- どちらにも StopWatch 固有の部品（CO5300 QSPI AMOLED、CST820 タッチ、IMU、IO エキスパンダー、I2S、本体ボタン）はない。
  `boards/board_*.c` にエミュレータ用の仮想ボードを足す必要がある。

#### 今後詰めること

- PSRAM 上のコード実行（ミニアプリの ELF）がエミュレータで動くか。まず今のファームを QEMU で起動して、どこまで進むか見る。
- Muse への接続（QEMU なら有線 LAN 経由、Wokwi なら Wi-Fi のまま行けるか）。
- 入力の注入と画面の取り出しの経路（シリアル、GDB、Wokwi の自動化）。
- より小さい代わり：実機に入力注入ツールと画面取得ツールを足し、Muse が実機を遠隔で操作する（エミュ不要）。

### 005：スペースから本体の画面を見て操作する（本体 API を IP 指定で使う）

- 記録日：2026-11-08

- やりたいこと：本体が API（画面の取得、タッチ・青ボタン・傾きの入力）を用意し、Muse がスペースに作るページから
  本体の IP を指定して使う。遊ぶときは Muse（LLM）を通らない、リモコンのようなもの。
- 呼びかけ例：「StopWatch の画面をスペースに出して、そこから操作できるようにして」

#### わかったこと（2026-11-08）

- スペースは自己完結かコネクタ経由。ガジェットのツールは Muse の CLI からだけ。VM のファイルは読むだけ（ユーザー調べ）。
  → スペースのサーバーやファイル経由では本体に届かない。ブラウザの JS から本体を直接呼ぶしかない。
- 試験：本体に `GET/OPTIONS /api/ping`（鍵なし・CORS *・Allow-Private-Network）を足して確認（msw_net.c）。
  - スマホの Safari（Muse アプリ内、Origin `hatch-spaces://<id>.metaaivm.com`）：届いて表示できた。
  - PC の Chrome：スペースからはだめ。本体に届いていない（送る前に止められた）。fetch の工夫もだめだった。
    PC の Chrome でアドレスを直接開くと届く（origin なし）ので、ネットワークではなく Chrome の制限
    （https→http の混在、ローカル網アクセス制限、CSP の upgrade-insecure-requests のどれか。特定できず）。
  - Android は未確認（Chrome なら同じ見込み。Muse アプリ内の表示なら iPhone と同じく通る可能性もある）。

#### 今後詰めること

- 本体を https / wss にする（自己署名、最初に一度ブラウザで許可）と Chrome で通るか。
- スマホ（Safari）だけでよいなら、このままの http で API を作れる。
- 画面の送り方（縮小・JPEG・変化した所だけ）と、入力の注入の仕組み（msw_touch・ボタン・IMU を差し替える）。
- Muse に教える方法：API の Doc と、本体の今の IP を返すツール（例 `web.info`）。
